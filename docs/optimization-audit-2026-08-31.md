## 1. 结论摘要

项目目前已经具备较完整的功能、权限边界、后台任务和测试基础，AI Provider、Runner、工具注册器、账号查询等核心包的 Go 测试覆盖也明显高于一般业务项目。当前最值得投入的方向不是继续增加功能，而是补齐以下四类结构性短板：

1. **先处理安全基线**：升级存在可达漏洞的 Go 运行时与依赖，拒绝示例会话密钥，保护首次初始化接口，并给开放门户补齐请求体和全局限流。
2. **让后台任务可恢复**：助手消息处于 `processing` 或 `sending` 时若进程退出，目前可能永久滞留；多副本默认 Master 还会带来重复采集和会话并发问题。
3. **保证数据口径可信**：多实例历史指标可能在缺失某实例数据时仍被标记为完整；实时历史写入失败也会被静默忽略。
4. **治理前端回归和请求规模**：门户筛选存在请求竞态，账号管理“全部实例”会产生无上限并发请求，前端 405 个 TS/TSX 文件目前只有 2 个测试文件。

### 优先级说明

- **P0**：已确认的高风险安全问题，或在特定生产配置下可直接导致权限绕过，应立即处理。
- **P1**：会造成数据错误、任务永久丢失、明显性能问题或核心流程中断，应进入近期版本。
- **P2**：可维护性、体验、可观测性和成本优化，可排入后续迭代。

## 3. P0：立即处理

### P0-1 升级 Go 运行时和 `x/text`

**证据**

- `Dockerfile:11` 使用 Go `1.26.1`。
- `go.mod:32` 使用 `golang.org/x/text v0.38.0`。
- 本次 `govulncheck ./...` 确认代码可达 `GO-2026-6218`、`GO-2026-6090`、`GO-2026-6089`、`GO-2026-6088`、`GO-2026-5972`、`GO-2026-5970` 和 `GO-2026-5026`。

**影响**

涉及 HTTP/TLS、URL、XML/ASN.1、Passkey 和 Excel 调用链，风险包含 CPU/内存拒绝服务、输入处理异常和 TLS 行为问题。

**建议**

1. 将开发、CI、Docker 和 Release 构建统一升级到 Go `1.26.6` 或更高安全补丁版本。
2. 将 `golang.org/x/text` 升级到 `v0.39.0` 或更高兼容版本。
3. 把 `govulncheck ./...` 和 `bun audit --production` 加入 CI；对不可达或仅开发依赖的告警使用有到期时间的显式豁免。

**验收**

- `govulncheck ./...` 不再报告上述可达漏洞。
- 五个平台采集、Passkey、门户 XLSX、邮件和在线更新回归测试通过。

### P0-2 核查生产会话密钥，启动时拒绝示例值

**证据**

- `docker-compose.yml:15` 使用公开值 `replace-with-a-long-random-string`。
- `common/init.go:41` 只拒绝 `random_string`，不会拒绝 Compose 中的示例值或短密钥。
- `middleware/auth.go:20` 依赖服务端会话中的用户 ID建立权限身份。

**影响**

如果生产环境沿用了示例密钥，攻击者可能伪造已知用户的签名会话。若生产已使用高熵随机密钥，则该项降为 P1 配置加固。

**建议**

- 启动时拒绝所有文档示例值、空值和低于 32 字节的低熵密钥。
- HTTPS 生产环境强制 `SESSION_COOKIE_SECURE=true`；配置不满足时直接拒绝启动。
- 在线更新文档加入密钥生成与轮换步骤。

**验收**

- 默认 Compose 不提供可直接运行的固定秘密，改为 Docker Secret、`.env` 必填或启动生成并持久化。
- 使用公开示例密钥构造的 Cookie 无法通过任何管理员接口。

## 4. P1：近期版本

### P1-1 首次初始化接口存在 Root 抢注窗口

**证据**：`router/api-router.go:24` 暴露 `POST /api/setup`；`controller/setup.go:35` 允许未初始化系统直接创建 Root，Root 检查、用户创建和 Setup 写入不在同一事务或互斥区间。

**风险**：全新数据库在公网可访问时，任意远程请求可抢先完成初始化；并发请求也可能形成不一致状态。

**建议**：要求一次性启动令牌或仅允许回环/可信管理网初始化；使用事务、唯一初始化记录和数据库锁实现原子初始化。

**验收**：非可信来源无启动令牌时无法初始化；两组并发初始化请求只能有一组成功。

### P1-2 开放门户缺少统一请求体限制和全局限流

**证据**：`router/account-data-api-router.go:25` 将 `/open-api` 和 `/open-portal` 直接挂到 Engine；`router/api-router.go:18` 的全局 API 限流与匿名 Body 限制仅作用于 `/api`；`controller/account_data_portal.go:24` 直接解析登录 JSON。

**风险**：开放路由可被超大 JSON、慢速请求或高频访问消耗连接、内存和 CPU。

**建议**：为两个开放路由组增加独立的请求体上限、IP/授权级限流、服务器 `ReadHeaderTimeout` 和合理的 `ReadTimeout`；登录 Body 可限制在 4 KB 以内。

**验收**：超限请求快速返回 `413`；慢速请求不长期占用连接；开放 API在多节点下使用统一限流口径。

### P1-3 门户限流可通过重新登录创建新会话绕过

**证据**：`service/accountdataapi/portal.go:119` 每次成功登录创建新会话；`controller/account_data_portal.go:81` 的查询限流键基于会话；`service/accountdataapi/portal.go:432` 的失败登录记录只保存在进程内 Map。

**风险**：持有门户密码的用户可以反复登录获得新限流桶；重启或多节点会绕过登录失败限制。

**建议**：查询限流键改为 `authorization_id + client_ip`，API Key继续按 Key；登录失败限制迁移到 Redis 或数据库 TTL 记录，并给内存降级实现设置容量上限。

**验收**：同一门户创建多个会话后，总请求量仍受同一授权限额约束。

### P1-4 助手任务在进程中断后可能永久滞留

**证据**：`service/assistant/processor/processor.go:383` 和 `:422` 将任务更新为 `sending/processing`；`service/assistant/worker/worker.go:189` 只扫描 `pending/failed`。

**风险**：进程在状态更新后、完成前崩溃或在线升级时，用户消息或最终回复不会再次执行。

**建议**：增加 `claimed_at`、`lease_until`、`claim_token`；启动和定时恢复过期 Claim；发送结果不确定时使用稳定消息 ID或 `unknown` 状态，避免恢复后重复发送。

**验收**：分别在领取后、模型调用中、微信发送后模拟退出，重启后任务可恢复且最终消息最多投递一次。

### P1-5 同一微信会话可能乱序，并占满全局并发槽

**证据**：`service/assistant/worker/worker.go:209` 先占用全局工作槽；`service/assistant/processor/processor.go:120` 和 `:297` 随后才使用进程内哈希锁串行会话。

**风险**：同一用户连续消息可能争抢锁而乱序，等待锁的任务仍占用全局槽，其他用户可能被饿死；多节点时进程内锁无效。

**建议**：按 `(channel_id, peer_id)` 建立数据库有序队列；先取得会话所有权，再占用模型执行槽；多节点使用会话租约。

**验收**：一个用户连续发 20 条消息时顺序稳定，同时另一个用户仍能及时查询 RPM。

### P1-6 多副本默认 Master 会重复采集与迁移

**证据**：`common/init.go:70` 在未配置 `NODE_TYPE` 时默认 Master；`main.go:122` 启动多个采集器；会话锁仍是进程内锁；`model/main.go:175` 的迁移也可能由多个 Master 同时执行。

**风险**：N 个副本可能产生 N 倍上游采集、重复任务和同一对话并行处理。

**建议**：采集器、迁移和调度器统一使用数据库或 Redis Leader Lease；启动时检测多个 Master 并告警；无 Redis 时也应有数据库租约降级。

**验收**：启动 3 个副本时只有 1 个节点采集和调度，Leader 失效后在租约时间内自动切换。

### P1-7 系统任务 Claim 数量远大于实际执行容量

**证据**：`service/system_task.go:252` 一次读取 100 条，`:290` 为每条启动协程并续租；账号采集并发仅 2（`service/managed_account_snapshot.go:632`），探测默认 8（`service/managed_instance_task.go:801`）。

**风险**：大量任务会提前显示运行，并创建大量等待协程、Ticker 和数据库续租写入。

**建议**：Claim 前先计算各任务类型可用容量，只领取可立即执行的数量；增加全局运行任务上限和排队时长指标。

**验收**：1,000 条任务积压时，运行协程和续租写入接近实际并发 2～8，而不是接近积压量。

### P1-8 账号查询对全部快照执行重复解码、排序和写入

**证据**：`service/managedaccount/query.go:262` 遍历实例；`service/managed_account_snapshot.go:316` 解码后，`query.go:299` 或 `:319` 再读取解码；`query.go:340` 对完整结果排序汇总后才分页；读取还会在 `managed_account_snapshot.go:330` 更新访问时间。

**风险**：即使只返回 20～50 条，也会产生 O(全部账号) 内存、O(A log A) 排序和每实例数据库写，SQLite 下尤其容易形成锁竞争。

**建议**

1. 短期：同一请求只解码一次；访问时间按小时节流或异步批量写。
2. 中期：建立可索引的账号投影表，采集时 Upsert，查询时数据库筛选、排序、分页和聚合。
3. 门户、AI、开放 API继续复用同一领域查询，避免重新产生三套口径。

**验收**：100 个实例、每实例 1,000 个账号时，返回 50 条不再排序 10 万行，也不会产生 100 次读取触发的 UPDATE。

### P1-9 `query_metrics` 多实例缺失数据可能仍显示完整

**证据**：`service/assistant/builtin/metric_history.go:600` 只聚合已存在 Dashboard 快照；`:394` 主要按桶统计；`query_metrics.go:245` 根据返回状态设置 `Complete`。

**风险**：某个实例整天无数据时，其余实例仍会被求和，并可能被回答成“完整”，导致消费、请求数和 Token 偏低。

**建议**：按“时间桶 × 所选实例”计算覆盖率；任一实例缺失时返回 `partial` 和缺失实例列表；真实零值通过样本或存在标志与缺失区分。

**验收**：两实例场景下，“一个无快照”“一个真实为零”“一个缺一天”返回三个不同状态。

### P1-10 AI 授权范围缩小后仍加载旧对话数据

**证据**：`service/assistant/binding/service.go:115` 更新身份范围；`service/assistant/processor/processor.go:341` 仍按会话加载最近 12 条；`:458` 将历史放入模型上下文。

**风险**：用户失去某实例权限后，模型仍可能从旧回答中复述该实例的邮箱、账号或指标。

**建议**：给授权范围增加版本号；范围变化、解绑或重新绑定时切换上下文版本；只加载当前授权版本产生的消息。

**验收**：先查询全实例敏感数据，再缩小权限并要求“重复上一条”，Provider 请求中不得出现旧数据。

### P1-11 门户筛选存在旧请求覆盖新请求的竞态

**证据**：`web/default/src/features/account-data-portal/index.tsx:207` 的 `load()` 没有 AbortSignal 或请求序列校验；`account-data-portal/api.ts:73` 也未暴露取消能力。

**风险**：连续修改筛选时，较早请求可能较晚返回并覆盖最新结果；列表、总金额和导出条件会不一致。

**建议**：迁移到 TanStack Query，以完整筛选快照作为 `queryKey`，使用 `AbortSignal` 取消旧请求；至少增加 request ID，只接受最后一次响应。

**验收**：人为让旧筛选请求延迟，最终列表、汇总、总金额和导出快照必须始终对应最新筛选。

### P1-12 任意后台查询的 500 会跳转整站错误页

**证据**：`web/default/src/main.tsx:88` 对任意 QueryCache 500 导航到 `/500`，包括后台刷新和非关键查询。

**风险**：一次瞬时 API故障就会中断用户正在编辑的表单或筛选状态。

**建议**：只有路由首屏关键请求触发错误页；后台刷新保留最后成功数据并显示局部告警，表单提交留在当前上下文。

**验收**：让预警、账号或审计后台刷新返回一次 500，页面不跳转且用户输入不丢失。

### P1-13 账号管理“全部实例”产生无上限并发请求

**证据**：`web/default/src/features/managed-accounts/index.tsx:812` 为每个实例建立独立 `useQueries`，未限制并发。

**风险**：100 个实例可能同时产生约 100 个快照请求，浏览器、反向代理、数据库和服务端解码同时承压。

**建议**：优先新增批量快照查询；过渡期在客户端按 4～8 并发分批请求，并渐进合并结果。

**验收**：100 个实例下首屏并发请求不超过设定阈值，页面可渐进展示且不阻塞操作。

### P1-14 前端关键流程缺少自动化回归保护

**证据**：`web/default/package.json:6` 没有 `test` 脚本；405 个 TS/TSX 文件仅有 2 个测试文件；`.github/workflows/quality.yml` 未运行前端测试。

**风险**：门户登录、筛选、编辑、导出、跨页选择、移动端和 AI 审计等交互回归只能靠手工发现，这与近期反复出现的页面问题相符。

**建议**

- Vitest + Testing Library：筛选、表单恢复、请求竞态、状态机和错误分支。
- Playwright：门户登录、授权编辑、跨页全选与导出、预警、移动端关键路径。
- CI 增加 `bun test`，并逐步设关键模块覆盖门槛，不追求无意义的全局 80%。

**验收**：每次 PR 自动覆盖上述核心路径；本轮发现的前端问题均有回归测试。

## 5. P2：后续优化

### P2-1 AI 历史上下文改为 Token 预算，而不是固定 12 条

`service/assistant/processor/processor.go:34` 固定加载 12 条消息，无法控制超长回答；工具循环在 `service/assistant/runner/runner.go:155` 重复携带系统提示、历史和工具定义。这是“只问两句但输入 Token 很高”的剩余原因。

建议按完整问答轮次实施 Token/字节预算，优先保留最近用户问题；大型工具结果只传必要字段和结构化摘要，并记录每部分 Token占比。

### P2-2 复用模型 HTTP Client

`service/assistant/processor/processor.go:186` 每条消息解析模型配置，`service/assistant/profile/service.go:209` 创建 Client/Transport，连接池无法稳定跨消息复用。

建议按“配置 ID + 更新时间 + 密钥版本”缓存只读 Client，配置变化时关闭并替换旧 Transport。验收指标是连续请求能够复用 TCP/TLS 连接，首包时间明显下降。

### P2-3 首包前重试改为“确定未写出才重试”

`service/assistant/provider/openai_compatible.go:148` 和 `:233` 以是否收到流数据判断重试，但请求可能已被上游接收，只是响应在首包前断开。

建议使用 `httptrace.WroteRequest` 区分未发送与结果不明；结果不明默认不重试，只有支持幂等键的供应商才安全重试，避免重复计费。

### P2-4 流式失败保留已确认 Usage

`service/assistant/provider/openai_compatible.go:342`、`:413` 和 `runner.go:170` 在流式错误时可能丢掉已收到的 Usage，审计显示 0 Token。

建议让错误结果携带 partial usage、首包状态和已完成工具轨迹；Runner 在成功或失败路径都先累计已确认值。

### P2-5 实时历史写入失败不能静默

`service/managed_sub2_realtime.go:256`、`service/managedinstance/conductor_rpm_history.go:81` 和 `:278` 丢弃写入或清理错误。

建议增加限频错误日志、写入失败计数、最后成功写入时间和滞后告警；只对可重试数据库错误进行短退避。

### P2-6 SSE 增加版本号与缺口重同步

`service/managed_dashboard.go:664` 在缓冲满时直接丢事件；`service/managed_realtime.go:173` 丢最旧事件。

建议按实例与主题合并最新状态，增加单调版本号；客户端发现版本缺口时重新读取快照，并记录丢弃指标。

### P2-7 访问日志改为后台分批清理并可靠记录

`service/accountdataapi/service.go:413` 在鉴权路径触发清理检查，`:531` 删除未分批，`:501` 忽略访问日志写入错误。高频授权 90 天可产生数百万条日志。

建议由 Master 定时游标分批清理；增加 `(api_id, created_at, id)` 索引；安全审计至少记录失败指标，关键管理审计使用事务 Outbox。

### P2-8 预警 CSV 防公式注入

`service/billingalert/export.go:83` 将实例名、规则名、条件和收件人直接写入 CSV；现有 `service/managedinstance/usage_records.go:1359` 已有可复用的防护方式。

建议所有文本字段统一转义以 `=`, `+`, `-`, `@` 开头的值。

### P2-9 对外备注脱敏增强

`service/managedaccount/query.go:27`、`:382`、`:826` 的规则主要覆盖 IPv4、URL、Bearer、`sk-` 和带标签秘密，IPv6和非标准长密钥可能漏出。

建议在统一输出边界增加 IPv6、常见云密钥和高熵长 Token检测；备注继续默认不开放，开放时明确提示风险。

### P2-10 门户筛选选项使用分页前全集

`web/default/src/features/account-data-portal/index.tsx:269` 从当前页 `result.items` 生成分类选项，而分类字段不允许自由输入，第二页独有的分组、节点或类型无法选择。

建议查询响应增加分页前的 `filter_options`，或提供只返回授权范围内选项的独立接口。

### P2-11 访问日志补充分页和错误态

`web/default/src/features/account-data-apis/index.tsx:1506` 只加载默认第一页，没有分页，也没有独立错误态，失败会看起来像“暂无记录”。

建议增加分页、总数、重试和错误提示，并避免一次渲染全部日志。

### P2-12 只挂载当前设备视图

门户、使用记录和预警记录仍使用 CSS 隐藏桌面或移动端视图，例如 `account-data-portal/index.tsx:556`、`usage-records/index.tsx:985`、`billing-alerts/records.tsx:431`，React 实际创建两套节点。

建议使用媒体查询只挂载一种视图。该项对 50～100 条列表可直接减少约一半行节点和格式化工作。

### P2-13 搜索请求增加延迟与取消

`account-data-apis/index.tsx:301` 和 `billing-alerts/records.tsx:310` 在搜索输入变化时直接请求。

建议增加 250～400ms debounce 或 `useDeferredValue`，同时取消旧请求；连续输入 10 个字符时请求应收敛到 1～2 次。

### P2-14 控制首屏资源与无用依赖

`web/default/rsbuild.config.ts:26` 的强制共享组让首屏 gzip 约 625 KB；`knip` 还报告未使用文件、依赖和导出。

建议先移除确认无用代码与依赖，再用 bundle analyzer 调整共享组；二维码、Motion、Markdown/KaTeX 等只在对应页面懒加载。建议将登录页和门户登录页首屏 gzip 控制在 300 KB 左右，并在 CI 增加 bundle budget。

### P2-15 pprof 仅监听本机

`main.go:140` 在 `ENABLE_PPROF=true` 时使用默认 mux 监听所有网卡的 `:8005`，没有认证。

建议改为独立 mux 监听 `127.0.0.1:8005`，生产环境通过 SSH 隧道或受保护的管理入口使用。

### P2-16 在线更新增加独立签名

`pkg/systemupdate/manager.go:254` 和 `:317` 校验与二进制同源发布的 SHA-256；`.github/workflows/release.yml:83` 同时发布校验和。

校验和能发现传输损坏，但不能抵御仓库或 Release 权限被攻破。建议使用离线私钥签名、程序内置公钥验证，并把所有 GitHub Action 固定到完整提交 SHA。

## 7. 建议验收指标

| 目标 | 指标 |
| --- | --- |
| 安全基线 | `govulncheck` 无可达高风险漏洞；生产无法使用示例会话密钥启动 |
| 助手可靠性 | 进程任意阶段退出后无永久 `processing/sending`；同一入站消息最终最多一条回复 |
| 多节点 | N 个副本始终只有 1 个采集 Leader；会话不跨节点并行 |
| 指标正确性 | 多实例任一缺失均标记 `partial`；真实零值不被当缺失 |
| 账号查询 | 100×1,000 账号查询不再全量重复解码和排序；P95 有明确基线和目标 |
| 前端请求 | 全部实例模式并发不超过 8 或只使用 1 个批量请求 |
| 门户一致性 | 快速切换筛选时列表、总金额和导出范围始终一致 |
| 前端质量 | CI执行单元测试和关键 Playwright 流程；所有已知交互回归均有测试 |
| 首屏性能 | 登录页/门户登录页首屏 gzip 约 300 KB 或更低 |
| 可观测性 | 历史写入、审计写入、SSE 丢弃、队列滞后均有指标和告警 |

## 8. 暂不建议的改动

1. **不建议立即拆微服务**：当前问题主要是租约、查询模型、前端状态和测试不足，拆服务会放大分布式复杂度。
2. **不建议重新引入“文档检索工具路由”**：统一 `query_metrics` 的方向正确，继续优化工具输出和上下文预算比增加一次检索调用更有效。
3. **不建议为了覆盖率补空洞测试**：优先保护门户、授权、导出、AI队列、指标完整性和多节点租约等真实回归路径。
4. **不建议用浏览器缓存掩盖账号查询问题**：门户、AI和开放 API都依赖同一后端查询，根因应在快照解码与投影层解决。
